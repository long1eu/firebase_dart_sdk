# tool/

- `test_all.sh [package ...]`: for the packages of `PACKAGES` (secure_flow, firebase_app_dart, firebase_auth_providers_dart, cloud_firestore_dart, firebase_storage_dart, firebase_auth_secure_storage_dart and others): `dart pub get`, `dart analyze lib` (errors and warnings fail it, infos are counted) and `dart test` (only `test/unit` for cloud_firestore_dart; all of `test/` for firebase_storage_dart, whose emulator, kit and browser tests skip themselves without their environment, and for firebase_auth_secure_storage_dart, whose integration tests against the real secret store skip themselves without `FIREBASE_AUTH_SECURE_STORAGE_INTEGRATION=1`). Then, for each example package in `examples/`: `dart pub get` and `dart analyze` of the whole package, where any issue, infos included, fails it; their tests are not run, since they need an emulator. Then the Flutter packages (`cloud_firestore_dart_flutterfire`, `cloud_firestore_dart_platform`, `firebase_auth_dart_platform`, `firebase_storage_dart_platform`, `firebase_auth_secure_storage_flutter`): `flutter pub get`, `flutter analyze` and `flutter test` (the emulator tests of the Firestore platform package run only with `FIRESTORE_EMULATOR_HOST`, those of the Auth one only with `FIREBASE_AUTH_EMULATOR_HOST`); a Flutter example is resolved and analyzed with `flutter`. Without `flutter` on the PATH these are skipped, or fail with `TEST_ALL_REQUIRE_FLUTTER=1`. Names select what runs: a package name, `examples` for all the examples, or `examples/<name>` for one. `TEST_LOG_DIR` keeps the outputs.
- `check_figures.dart`: `dart tool/check_figures.dart` from the repository root checks the SVG figures of `docs/images/` (shared light/dark palette, every colour mapped, contrast); see `docs/images/README.md`.
- `check_web_imports.dart`: `dart tool/check_web_imports.dart <package dir> [entry library...]` from the repository root fails when a library meant for the web reaches `dart:io` or `dart:ffi`, following the web branch of conditional imports through the package and its dependencies (needs `dart pub get`). Web compilers accept those imports, so a web compile does not catch them.
- `publish_first_version.sh <package> [git ref]`: publishes a package to pub.dev by hand from a clean copy of `origin/main` (or the ref), with no `pubspec_overrides.yaml`, so its dependencies resolve from pub.dev. It checks the `CHANGELOG.md` heading for the pubspec version, runs `pub get` and `pub publish --dry-run` (`flutter pub` for Flutter packages), then `pub publish`, which shows the archive and asks y/N. Use it for the first version of a new package, which pub.dev does not allow `publish.yml` to publish; later versions go out by tag. `DRY_RUN=1` stops after the dry run. It uses the pub.dev login of whoever runs it and never reads credentials.
- `print_test_failures.sh <log>`: the failed tests of a `dart test --reporter expanded` log with the first lines of each error; the test scripts call it on failure. The scripts name the expanded reporter because `dart test` switches to its `github` reporter under GitHub Actions.
- `start_emulator.sh`, `stop_emulator.sh`: run the Firestore emulator on 127.0.0.1:8080 (project `demo-test`).
  The Firebase CLI is installed locally in `.emulator/` (git-ignored): `mkdir -p .emulator && cd .emulator && npm init -y && npm install firebase-tools`.
  Override the location with `EMULATOR_DIR`. Java is required; the emulator JAR downloads on first start.
- `test_integration.sh [standard|enterprise|both] [dart test arguments...]`: run the cloud_firestore_dart integration tests against emulators that are already running (it never starts or stops one).
  - `standard` (default): `test/integration` against the Standard edition emulator (`FIRESTORE_EMULATOR_HOST`, default 127.0.0.1:8080).
  - `enterprise`: `test/integration` against the Enterprise edition emulator (`FIRESTORE_ENTERPRISE_EMULATOR_HOST`, default 127.0.0.1:8181), then `test/integration_enterprise`.
  - `both`: one after the other. Extra arguments replace the default paths, e.g. `tool/test_integration.sh enterprise test/integration/firebase/firestore/query_test.dart`.
  - `--transport=webchannel` (after the edition): run the same tests over the web transport (REST and WebChannel through `dart:io` HTTP) instead of gRPC, still on the VM. The standard suite passes over it against emulator v1.22.0, with the same counts as over gRPC. `--transport=webchannel-longpolling` does the same with the streams in long polling mode. In these runs the Firestore Lite tests (`test/integration/firebase/firestore/lite_test.dart`) use the transport the lite library has on the web (REST only, `rest_transport.dart`); `FIRESTORE_TEST_TRANSPORT=rest` selects it for that file alone.
  - The full output of each run goes to `TEST_LOG_DIR` (default: a new temp dir); the script prints the failed tests and a summary and exits non-zero on failure.
- By hand, from `cloud_firestore/cloud_firestore_dart`: `FIRESTORE_EMULATOR_HOST=127.0.0.1:8080 dart test test/integration`.
- `start_storage_emulator.sh [port]`, `stop_storage_emulator.sh [port]` (default 9299; the CLI's own 9199 is refused, like 8080, 8181, 9099, 4400 and 4500): run a private Firebase Storage emulator (project `demo-test`) through the Firebase CLI, with its own pid file, log, hub (port + 1) and logging (port + 2) ports.
  - Each emulator gets its own `TMPDIR` (`.emulator/tmp_<port>`): the emulator wipes `$TMPDIR/firebase/storage/blobs` on start, which would break other running Storage emulators.
  - Two buckets: `demo-test.appspot.com` with open rules (`tool/storage_emulator/open.rules`) and `demo-test-auth.appspot.com` whose rules (`tool/storage_emulator/auth.rules`) need a signed-in user (`users/<uid>/` only for that user, `shared/` for any user), for the 403 tests. Any other bucket answers 403 ("no loaded ruleset"). The data is in memory and is lost when the emulator stops.
  - The CLI is found as for the Auth emulators (`FIREBASE_CLI`, `.emulator/node_modules`, the PATH). The script refuses to start when `cloud-storage-rules-runtime-v*.jar` is not in `~/.cache/firebase/emulators` (run `firebase setup:emulators:storage` once), so nothing is downloaded. `STORAGE_HUB_PORT` and `STORAGE_LOGGING_PORT` move the two extra ports. The start script prints `export FIREBASE_STORAGE_EMULATOR_HOST=127.0.0.1:<port>`.
  - The stop script signals (SIGINT) only the recorded pid, and only while it still is that firebase process.
- `test_flutterfire_database_gate.sh [--dry-run] [--device <id>]`: the acceptance gate of `firebase_database_dart_platform`: FlutterFire's own `firebase_database` example integration tests (78) against the shim and the Realtime Database emulator. `FLUTTERFIRE_DIR` names a FlutterFire checkout at the pinned commit (`6a80b1b5`); the script copies the example and FlutterFire's `.github/workflows/scripts/database.rules.json` into a temporary directory (the checkout is never changed), patches the copy (drops `resolution: workspace`, pins `firebase_database` 13.1.0 and adds the shim by path; a `databaseURL` in `firebase_options.dart` and a Linux case in `DefaultFirebaseOptions`; a `gate_test.dart` that sets the target platform to Linux and calls `FirebaseDatabaseDart.use(useDartCore: true)` before FlutterFire's `main`; a `linux/` folder from `flutter create`), starts the emulator on 9000 (the port the suite hard-codes) with `start_database_emulator.sh`, loads the rules into the namespace `flutterfire-e2e-tests-default-rtdb` over the emulator's REST API, runs `flutter test integration_test/gate_test.dart` (`-d <id>` with `--device`) and fails on a failed test or on a skip count other than `EXPECTED_SKIPS` (2: the web-only and the Android-only test). `--dry-run` prints every step and file and changes nothing. The copy is kept when the gate fails.
- `bench_storage.sh [upload_benchmark.dart options]`: starts a private Storage emulator on 9480 (hub 9580, logging 9680), runs `firebase_storage/firebase_storage_dart/benchmark/upload_benchmark.dart --backend=emulator` with the given options (object sizes, chunked or single-request, added latency and bandwidth through a local proxy, concurrent uploads) and stops the emulator, also on failure. It prints a Markdown table and writes JSON to `benchmark/results/` (git-ignored). See `firebase_storage/firebase_storage_dart/benchmark/README.md`.
- `start_enterprise_emulator.sh`, `stop_enterprise_emulator.sh`: run a second Firestore emulator in **Enterprise edition** on 127.0.0.1:8181 (project `demo-test`), next to the standard one.
  - It runs the emulator JAR directly (`java -jar ... --database-edition enterprise`), without the Firebase CLI. The JAR is the newest `cloud-firestore-emulator-v*.jar` in `~/.cache/firebase/emulators` (the CLI downloads it on the first start of the standard emulator, or with `firebase setup:emulators:firestore`); set `FIRESTORE_EMULATOR_JAR` to use another one.
  - `ENTERPRISE_EMULATOR_PORT` changes the port, `EMULATOR_DIR` the directory of `enterprise_emulator.pid` and `enterprise_emulator.log` (default `.emulator/`).
  - The pid file holds the pid of that java process. The stop script signals only that pid, and only after checking that it still is a Firestore emulator started with `--database-edition enterprise`; it never touches the standard emulator. The start script refuses to start when the port is already taken by something else.
- Enterprise tests: `FIRESTORE_ENTERPRISE_EMULATOR_HOST=127.0.0.1:8181 dart test test/integration_enterprise` from `cloud_firestore/cloud_firestore_dart`. Without the variable they are skipped (with a reason). Tests that compare the two editions also need `FIRESTORE_EMULATOR_HOST`.
- Environment variables read by the tests (`cloud_firestore/cloud_firestore_dart/test/util/test_backend.dart`):

  | Variable | Meaning |
  | --- | --- |
  | `FIRESTORE_EMULATOR_HOST` | `host:port` of the standard emulator. When set it always wins over a real project. |
  | `FIRESTORE_ENTERPRISE_EMULATOR_HOST` | `host:port` of the Enterprise edition emulator, for `test/integration_enterprise`. |
  | `FIRESTORE_EMULATOR_EDITION` | `standard` or `enterprise`: the edition of the emulator behind `FIRESTORE_EMULATOR_HOST`. `test_integration.sh` sets it; with `enterprise` the tests of the standard suite whose expectations only hold for the Standard edition are skipped. Unset, the edition is Enterprise exactly when both host variables name the same emulator. |
  | `FIRESTORE_TEST_PROJECT_ID` | Opt-in: run the integration suite against this real Firebase project (only while `FIRESTORE_EMULATOR_HOST` is unset). |
  | `FIRESTORE_TEST_DATABASE_ID` | Optional database id in that project (default `(default)`). |
  | `GOOGLE_APPLICATION_CREDENTIALS` | Standard Application Default Credentials variable: path of a service-account key file used for the real project. Without it the gcloud application-default credentials are used. |

  The real-project mode is described in the Testing section of `cloud_firestore/cloud_firestore_dart/README.md`. It is never used unless you set `FIRESTORE_TEST_PROJECT_ID`.
- The standard suite on the Enterprise edition emulator (v1.22.0): everything passes except the tests listed below, which `tool/test_integration.sh enterprise` skips with a reason (behaviour differences of the edition, or emulator bugs):

  | Difference on Enterprise | Tests skipped |
  | --- | --- |
  | Equality filters (`in`, `array-contains`, `array-contains-any`) match `null` and `NaN`; on Standard they never do. | `query_test`: `testQueriesCanUseInFilters`, `testQueriesCanUseArrayContainsFilters`, `testQueriesCanUseArrayContainsAnyFilters` |
  | `sum` over no documents is `null`, not `0`. | `aggregation_test`: `testPerformsSumAndAverageOverZeroDocuments`; `composite_index_query_test`: `testPerformsAggregationWhenUsingArrayContainsAnyOperator` |
  | An aggregation covers every document of the query; Standard only aggregates over the documents that have all the aggregated fields. | `lite_test`: `performs aggregations on documents with all aggregated fields using getAggregationFromServer` |
  | No limit of 5 aggregations per query. | `aggregation_test`: `testCannotPerformMoreThanMaxAggregations` |
  | An integer `sum` that overflows 64 bits (also only while accumulating) fails with `INVALID_ARGUMENT: Long overflow`; Standard returns a double. | `aggregation_test`: `testPerformsSumThatOverflowsMaxLong`, `testPerformsSumThatIsNegative`, `testPerformsSumThatCanOverflowIntegerValuesDuringAccumulation` |
  | Emulator bug: a Listen with `!=` or `not-in` on the document id fails with `__key__ filter value must be a Key`, although the client sends a reference value and the identical query succeeds with RunQuery on the same emulator (and with Listen on the Standard one). | `query_test`: `testQueriesCanUseNotEqualFiltersWithDocIds`, `testQueriesCanUseNotInFiltersWithDocIds` |

  The first four rows are pinned by `test/integration_enterprise/edition_differences_test.dart`. All of this was observed with the emulator only, not with a production Enterprise database. The JS SDK skips its counterparts of rows 1 to 3 on Enterprise (`it.skipEnterprise`); it has no counterpart of row 4 with real 64-bit integers.
- **Web transport and the emulator.** Browser tests and `--transport=webchannel*` runs go to a private emulator, never to the shared one on 8080:
  - `start_private_emulator.sh [port]` / `stop_private_emulator.sh [port]` (default 8090) run the emulator JAR in Standard edition with their own pid file and log. `test_integration.sh --transport=webchannel*` defaults to 127.0.0.1:8090, and the browser tests are compiled for that port.
  - `build_web_test_assets.sh` fetches or builds the files the browser tests load at run time and that are not in the repository: `test/browser/sqlite3.wasm` (downloaded, accepted only with the sha256 pinned in the script) and `test/browser/crash/crash_worker.js` (compiled with `dart compile js -O1`, rebuilt when its sources changed). `test_browser.sh` and `test_unit_browser.sh` call it; new assets go there as one more section.
  - `test_unit_browser.sh` runs the unit tests of the SQLite layer (`test/unit/firebase/firestore/local/sqlite_*_test.dart`) in Chrome with dart2js, on the WebAssembly build of SQLite; no emulator. Four files are left out, with the reason in the script: two import `dart:io`, and `sqlite_field_index_manager_test.dart` and `sqlite_lru_garbage_collector_test.dart` each have one test that fails with dart2js.
  - `test_browser.sh [dart2wasm|dart2js|both]` runs `test/browser` in Chrome with `-j 1` and starts (and stops) the private emulator if needed, and the Auth emulator with the rules emulator of `start_auth_emulators.sh` on 9297 and 8297 (`AUTH_EMULATOR_PORT`, `AUTH_RULES_EMULATOR_PORT`) for `web_two_users_test.dart`, whose addresses it writes to `test/browser/auth_emulators.txt` (git-ignored); without a firebase CLI that test skips itself. `FIRESTORE_EMULATOR_PORT=<port>` picks another private emulator than 8090; the script writes it to `test/browser/emulator_port.txt` (git-ignored), which the tests read at run time (`test/browser/emulator_port.dart`), since a browser test cannot read the environment and `dart test` cannot pass defines. It passes the test files in name order (`web_persistence_reload_2_read_test.dart` must load after `..._1_write_test.dart`) and downloads `test/browser/sqlite3.wasm` for the persistence tests: the asset of the `sqlite3-<version>` release of `simolus3/sqlite3.dart` for the version in `pubspec.lock`, accepted only with the sha256 pinned in the script (update `SQLITE3_WASM_VERSION` and `SQLITE3_WASM_SHA256` together when the dependency moves; `SQLITE3_WASM=<file>` uses a local file instead). The persistence tests (`web_persistence*_test.dart`) need `test/browser/sqlite3.wasm`, the WebAssembly build of the resolved `sqlite3` version from the releases of that package (not in the repository); without it they skip themselves with a reason. `web_persistence_reload_2_read_test.dart` has to be loaded after `web_persistence_reload_1_write_test.dart` in the same run: pass the files in that order (the runner keeps the order of its arguments, not of a directory), otherwise the second one skips itself with a reason. `web_persistence_crash_test.dart` (300 kills of a worker in the middle of its writes, about 45 s) also needs `test/browser/crash/crash_worker.js`, compiled by `tool/build_web_test_assets.sh` (which `test_browser.sh` runs; the file is git-ignored and includes the example opener, so it is rebuilt every time), and its IndexedDB variant only runs with `-c dart2js`: under dart2wasm it skips itself with a reason. Its OPFS variant (300 more kills, the database in OPFS through `test/browser/opfs/sqlite_opfs_worker.js`, compiled by the same script) runs with both compilers; `web_persistence_opfs_test.dart` needs that worker too. The SQLite-backed unit tests (`test/unit/firebase/firestore/local/sqlite_*_test.dart` and the other tests on `DatabaseMock`) run in Chrome too, `dart test -p chrome -c dart2js <files>`, through `test/util/sqlite3_database_web.dart` (the WebAssembly SQLite on an in-memory file system); they need the same `sqlite3.wasm`.
  - `test_browser_storage.sh [dart2wasm|dart2js|both] [dart test arguments...]` runs `firebase_storage/firebase_storage_dart/test/browser` in Chrome (`-j 1`, both compilers by default) against a private Storage emulator on 9385 (`STORAGE_EMULATOR_PORT`; hub and logging take the next two ports). It starts the emulator with `start_storage_emulator.sh` if none answers and stops it again at the end, and writes the port to `test/browser/emulator_port.txt` (git-ignored) for the tests, as `test_browser.sh` does. The tests (`@TestOn('browser')`, tag `browser`, see the package's `dart_test.yaml`) use the client over `package:http`'s `BrowserClient` (fetch): putBytes, getBytes, metadata, list, delete, and `storage_cors_test.dart`, which checks that `X-Goog-Upload-Status`, `-URL` and `-Size-Received` of the resumable start and query answers are readable from JS (the emulator lists the `x-goog-upload-*` headers in `Access-Control-Expose-Headers`; the JS SDK reads exactly those three, and production's firebasestorage.googleapis.com exposes them too, so a client that works here works there; not re-checked against production). `storage_resumable_web_test.dart` is skipped with a reason until the resumable upload is merged. Without Chrome or the firebase CLI the script fails; it needs the storage rules runtime in `~/.cache/firebase/emulators` (see `start_storage_emulator.sh`).
  - Why private: the emulator (v1.22.0) keeps the socket of an aborted WebChannel back-channel request when the session was not terminated. Measured on a fresh emulator with 20 sessions each: handshake only, handshake + terminate, a long poll that completes, an aborted back channel followed by terminate, and terminate while the back channel is open leave nothing behind; an aborted back channel without terminate leaves one file descriptor per session, later listed by `lsof` as a `CLOSED` TCP socket, until a garbage collection of the emulator (20 went down to 2 in about four minutes; 38 others stayed for more than five).
  - The client caused them: when a client was terminated its HTTP layer was closed right after the terminate requests were issued, which cut them off. One run of `firestore_test.dart` (66 tests) over the web transport left 105 file descriptors (81 `CLOSED` sockets 45 s later) on a fresh emulator; with the fix (sessions are always terminated, also when closed during their handshake, and the HTTP layer waits for that) the same run leaves 4 and no `CLOSED` socket. A browser tab that is closed still cannot terminate its sessions.
  - Restart the private emulator after a few web runs. The emulator starts one thread per WebChannel session (`com.google.net.webchannel.server.common.ChannelProcessor.run`, seen with `jstack`) and never ends it, also when the session was terminated properly: 20 sessions of any kind add 20 threads, which were still there minutes later. One run of the standard suite over the web transport opens about 1100 sessions. On macOS a process may have 8192 threads (`kern.num_taskthreads`): the emulator then logs `pthread_create failed (EAGAIN)`, stops answering (requests time out, or REST answers 500 "Panic! This is a bug!") and finally exits. A private emulator died that way after about six suite runs plus the chaos tests; this is also what broke the shared emulator. The client cannot avoid it. `test_browser.sh` uses a fresh emulator when it starts one itself, and CI runs the two web suite modes in separate jobs, each on its own emulator.
  - A listen that returns more than about 10,000 documents fails over WebChannel on the emulator (v1.22.0), streaming or long polling: the emulator queues at most 10,000 messages for the back channel, logs `Failed to send a new message due to too many pending messagings in the back channel (10001)` and drops the session, which the client sees as HTTP 404 and `unavailable`. Measured on the VM with a collection of 12,000 documents: limits of 9,000 and 9,990 work, 10,500 and 12,000 fail; over gRPC all four work. In headless Chrome (dart2js and dart2wasm) a `get` of 20,000 documents fails the same way, while 20,000 documents read in pages of 500 or 1,000 (`orderBy(FieldPath.documentId)` with `startAfter` or `startAfterDocument`) all arrive. The JS SDK (13.3.0, in the same browser against the same emulator) fails too: `getDocsFromServer` with `unavailable` after about 34 s, and `getDocs` answers from the cache with 0 documents, as this SDK does with the default source. The client cannot avoid it (the messages pile up on the server); read large collections in pages against the emulator. Not checked: the production backend.
  - Why `-j 1` for the browser tests: Chrome allows six connections per host over HTTP/1.1, which is what the emulator speaks, and they are shared by all tabs. A client holds up to two long-lived requests (listen and write) plus its unary calls; a single test page was measured at up to 6 requests in flight and the three test files side by side at 5 + 6 + 6. Requests then wait in the browser: first tests failed with "Request time out" after the 15 s unary timeout, with `unavailable` on a server read, or with a listener that never synced, in about one parallel run out of six. Five serial runs in a row passed in 7 to 8 s each. The production backend speaks HTTP/2, where the limit does not apply (not verified).
- `check_size.sh` compiles the two programs of `tool/size` (the same small application with Firestore Lite, `lite_app.dart`, and with the main library and a memory cache, `full_app.dart`) with `dart compile js -O2` and prints the size of the JavaScript, raw and gzipped, and how much of it is code of `cloud_firestore_dart`. It fails when the compiler's `--dump-info` output lists code of the local store, the sync engine, the views, the remote store, bundles or the WebChannel transport in the lite program, or when a program is over its budget in `tool/size/check_size.dart`: lite 450,000 characters, 140,000 bytes gzipped (measured 415,850 and 128,303 with Dart 3.12.2); full 717,000 and 219,000 (measured 651,311 and 199,005, plus about 10%). The numbers move with the Dart SDK, so compare runs of the same SDK. `SIZE_OUT_DIR` keeps the compiled programs and the dumps.
- CI: GitHub Actions files in `.github/`, on `ubuntu-26.04` (named explicitly: it is the image `ubuntu-latest` resolved to in every run so far, and the jobs use its Chrome, libsqlite3 and openssl), except the signed macOS job on `macos-26`. Every action is pinned by commit (the release is in a comment), every workflow has `permissions: contents: read` (the path filter adds `pull-requests: read`; the signed macOS job has `contents: read` and `id-token: write` only), and no workflow uses a secret. Two composite actions do the common setup: `.github/actions/dart` (the Dart SDK and a cache of `~/.pub-cache` keyed on the SDK and every `pubspec.yaml`/`pubspec.lock`) and `.github/actions/emulators` (Java 21, Node 22, the Firebase CLI, and the Firestore emulator JAR cached per version of the CLI). Validate changes with `docker run --rm -v "$PWD:/repo" -w /repo rhysd/actionlint:1.7.7` (`.github/actionlint.yaml` declares the runner label).
  - `workflows/ci.yml`, on every pull request, every push to main and by hand. A newer push to a pull request cancels the run it supersedes; runs on main are never cancelled. The unit jobs start at once: `test_all.sh` on the lowest supported Dart (3.8.0, with the formatting check of `lib` and `example` and a run of `firebase_auth_providers_dart` on its lowest dependencies; a skipped test of `secure_flow` fails the leg on both SDKs) and on stable (plus the connectivity test that adds a network interface, as root, allowed to fail). Each SDK runs in two parallel legs (`unit-legs`, `unit-stable-legs`): `test_all.sh cloud_firestore_dart`, and `test_all.sh` with every other package of `PACKAGES` and `examples` (a package added to `PACKAGES` must be added to that leg too). The jobs `unit` and `unit-stable` keep the check names "Unit tests and formatting (Dart 3.8.0)" and "Unit tests (Dart stable)" and pass only when both legs of their SDK passed. The emulator suites wait only for the path filter, not for the unit jobs, and are skipped when every changed file is documentation (`*.md`, `docs/`, LICENSE, NOTICE; a skipped job counts as passed): the standard suite plus `test/production` (`test_integration.sh standard`), the same over the web transport and, in a second job in parallel, with long polling, each against its own private emulator, the Enterprise tests (`test/integration_enterprise` with both emulators) and the standard suite on the Enterprise emulator. The standard jobs install `interop/` so that the JS interop tests run. The browser tests (`test_browser.sh dart2wasm`, in headless Chrome against its own private emulator on 8090) also wait only for the path filter, and only run when a change touches what they cover: `lib/`, `test/browser/`, `pubspec.yaml` or `pubspec.lock` of `cloud_firestore_dart`, `lib/`, `bin/` or `pubspec.yaml` of `cloud_firestore_dart_sqlite` (the web opener and the OPFS worker the tests use), the scripts they use (`test_browser.sh`, `build_web_test_assets.sh`, the private emulator scripts, `print_test_failures.sh`), `ci.yml` or `.github/actions/`; the job uploads its logs when it fails. The IndexedDB cache interop job (`indexeddb-interop`) waits only for the path filter too and runs `bench/web_idb/js_import/interop_check.sh` (the official JS SDK and the IndexedDB engine on one database in headless Chrome, both ways) against a private emulator on 8395, after `npm ci` of that directory's `package-lock.json` (the firebase JS SDK and esbuild); it only runs when a change touches the engine (`lib/indexeddb_cache.dart`, `indexeddb_cache_settings.dart`, `local/indexeddb/`, `index/js_index_value_writer.dart`, `pubspec.lock` of `cloud_firestore_dart`), `bench/web_idb/js_import/`, the private emulator scripts, `ci.yml` or `.github/actions/`. The Storage job (`storage`) waits only for the path filter, downloads the rules runtime (`firebase setup:emulators:storage`), starts `start_storage_emulator.sh 9299` starts the Auth emulator (`start_auth_emulators.sh 9398 9397`) and runs `test/integration` and `test/production` of `firebase_storage_dart` with `FIREBASE_STORAGE_EMULATOR_HOST=127.0.0.1:9299` and `FIREBASE_AUTH_EMULATOR_HOST=127.0.0.1:9398`; a skipped test fails it (the emulator did not reach it). `firebase_storage_dart` also joins the `others` leg of both unit jobs (its tests and the format check of `lib` and `test`), and so does `firebase_auth_secure_storage_dart` (its unit tests; its integration tests skip there, and the format check of `lib` and `test`). The size check (`check_size.sh`, on Dart 3.12.2) only waits for the path filter. The Flutter job (`flutter`, Flutter stable via `subosito/flutter-action`) waits only for the path filter like the emulator suites and runs `test_all.sh cloud_firestore_dart_flutterfire cloud_firestore_dart_platform firebase_auth_dart_platform firebase_storage_dart_platform firebase_auth_secure_storage_flutter examples/flutter_notes examples/flutter_web_two_users` with `TEST_ALL_REQUIRE_FLUTTER=1` against a private emulator on 8090; `test_all.sh` also builds a Flutter example that has a `web/index.html` with `flutter build web` and `flutter build web --wasm`. The secure storage jobs (`secure-storage-linux`, `secure-storage-windows`, `secure-storage-macos`) wait only for the path filter and run only when a change touches `firebase_auth_secure_storage_dart`, `ci.yml` or `.github/actions/`: the integration tests of that package against the real store, with `FIREBASE_AUTH_SECURE_STORAGE_INTEGRATION=1`, as its README describes them: on Ubuntu with libsecret and gnome-keyring in `dbus-run-session` (the no-bus case runs inside that test), on Windows with DPAPI (setup-dart directly, Bash), on macOS with the login keychain; each fails when no test passed or one was skipped. Required (no `continue-on-error`): both unit jobs, the Flutter job, the Storage job, the standard suite over gRPC, over the web transport and with long polling, the Enterprise tests, the browser tests, the IndexedDB cache interop and the Linux and Windows secure storage jobs. Allowed to fail: the standard suite on the Enterprise emulator, the size check and the macOS secure storage job (until it has passed on a runner).
  - `workflows/nightly.yml`, every night at 03:17 UTC and by hand: the slow and opt-in suites. The scale soak in a short configuration (`SCALE_SOAK_SECONDS=120`, two isolates of three clients), the property tests with `PROPERTY_SCALE=20` (unit, standard emulator, and Enterprise with both emulators), the browser tests on dart2wasm and dart2js (`test_browser.sh both`, then `test_unit_browser.sh`), the unit suite in a Linux amd64 container (`linux/run_in_container.sh unit linux/amd64`) and the Firebase Auth emulator tests (`start_auth_emulators.sh`, the VM and browser tests of `firebase_auth_providers_dart`, `test/auth_emulator_test.dart` of `firebase_admin_dart`, and `test/integration_auth`). Each job uploads its logs when it fails.
  - `workflows/release.yml`, on a tag `v<version>` (all three packages) or `<package>-v<version>` (one), or by hand with a tag: for each package, in dependency order (`secure_flow` for its own tag, then `firebase_app_dart`, `firebase_auth_providers_dart`, `cloud_firestore_dart`), the pubspec version matches the tag, `CHANGELOG.md` has a `## <version>` heading, and `dart pub publish --dry-run` passes. It never publishes: publishing to pub.dev is a manual step the maintainer runs and approves, and the workflow has no pub.dev credentials.
  - `workflows/secure_storage_signed_macos.yml`, on a push to main that touches `firebase_auth_secure_storage_flutter` (with its `example/`) or the workflow, and by hand; never on a pull request. The integration tests of `firebase_auth_secure_storage_flutter/example` (`flutter test integration_test -d macos`) against the real data-protection keychain, in the example app signed with a Developer ID certificate and profile (a development profile would run only on registered Macs, and each hosted runner is a new one). The job uses the `signing` environment (main only, the owner approves each run). It authenticates to Google Cloud by Workload Identity Federation (`google-github-actions/auth`, a service account that can only read `gs://flutter-sdk-match`), resolves the dependencies from the lock files first (`flutter pub get --enforce-lockfile`, and `pod install` must leave `Podfile.lock` unchanged), then fetches the certificate and the profile `match Direct dev.upcode.firebaseAuthSecureStorageExample macos` with `fastlane match developer_id --readonly` (into a staging keychain it deletes at once), imports the key into a signing keychain with `codesign` as its only trusted application and the partition list `apple-tool:,apple:`, deletes both keychains in an `if: always()` step, and selects the profile with `macos/Runner/Configs/Signing.local.xcconfig` (with `CODE_SIGN_INJECT_BASE_ENTITLEMENTS = NO`: Debug would add `get-task-allow`, which a Developer ID profile does not allow). No secrets and no notarization credentials: match does not encrypt that bucket and does not call App Store Connect in readonly mode. It uploads nothing: nothing signed leaves the runner. The package README ("Signed integration tests") has the details and the local run.
  - `dependabot.yml`: weekly updates, one grouped pull request for the pub dependencies of the three packages and one for the GitHub Actions (the workflows and the two composite actions).
- Chaos tests: `test/integration/firebase/firestore/chaos/` in `cloud_firestore/cloud_firestore_dart` puts a test-only TCP proxy (`test/util/chaos_proxy.dart`) between a client and the emulator and cuts, stalls or delays the connection. They run with the integration suite (emulator only). The randomized soak test is short by default: `CHAOS_SOAK_SECONDS` (default 4), `CHAOS_SOAK_CLIENTS` (default 3) and `CHAOS_SOAK_SEED` make it longer or repeat a run; on failure it prints the seed and the log of the operations. They also run over the web transport (`--transport=webchannel` and `webchannel-longpolling`, the proxy is at TCP level): every scenario passes there except one that is skipped with a reason (it needs two increments in flight at once, and the web transport never sends an increment before the answers to the earlier writes arrived).
- `start_auth_emulators.sh`, `stop_auth_emulators.sh` `[auth port] [firestore port]` (defaults 9197 and 8197): the Firebase Auth emulator (needs the firebase CLI, see above) and a private Firestore emulator whose rules require a signed-in user (`auth_emulators/firestore.rules`), for `firebase_auth/firebase_auth_providers_dart/test/auth_emulator_test.dart` and `cloud_firestore/cloud_firestore_dart/test/integration_auth`. The start script prints the two variables to export (`FIREBASE_AUTH_EMULATOR_HOST`, `FIRESTORE_AUTH_RULES_EMULATOR_HOST`); the tests are skipped without them. Each emulator is stopped by its own pid; the shared emulators and their rules are not touched. The firebase CLI also opens a hub and a logging port for the Auth emulator; they default to the auth port + 1 and + 2 (not the CLI's 4400 and 4500) and can be set with `AUTH_HUB_PORT` and `AUTH_LOGGING_PORT`.
- `linux/run_in_container.sh [suites] [linux/arm64|linux/amd64]`: the unit tests (`test_all.sh`) and the integration suites in a Linux container. `suites` is a comma-separated list of `unit`, `integration` (`test_integration.sh standard`), `web` (the same over the web transport, then long polling, each on a fresh emulator) and `enterprise` (`test_integration.sh enterprise`, with an Enterprise edition emulator on 8181 next to the standard one); `all` is all four, the default `unit,integration`. The image is built from `linux/Dockerfile`: `dart:stable` on Debian, Java 21, only the runtime package of SQLite. The emulator runs inside the container from the JAR in `~/.cache/firebase/emulators` (copied in, never modified), so no emulator of the host is used. The container gets `CAP_NET_ADMIN` and `FIRESTORE_TEST_NET_ADMIN=1` for the connectivity test that adds a network interface (`connectivity_interface_change_test.dart`). It is named `fsdart-linux-test-<arch>-<pid>` and removed on exit; logs go to `TEST_LOG_DIR`. The platform that is not the one of the Docker server runs emulated. On an Apple silicon Mac (Rosetta), x64 fails three unit tests every time, all sensitive to how fast code first runs: `exponential_backoff_test` (first attempt under 50 ms), `task_scheduler_test` `canScheduleTasksInTheFuture` (timers 4 ms apart) and `cancelled_call_close_test` (times out); they pass natively on arm64, and the unit job of CI runs them on x64.
- `interop/`: Node harness for the interop tests with the JS SDK and firebase-admin (`npm install` there; see its README).
- `bench/`: micro-benchmarks for hot paths.
- Regenerating the Firestore protos: `cloud_firestore/cloud_firestore_dart/tool/gen_protos.sh` (needs `protoc_plugin` 25.1.0, matching protobuf 6.x; set `PROTOC_GEN_DART` to use a `protoc-gen-dart` that is not on `PATH`). The well-known types (`google/protobuf/*.proto`) are not generated: they come from `package:protobuf/well_known_types`. If `protoc` is unusable, set up `tool/protoc_wrap.sh` (see its header) and pass `PROTOC="$PWD/tool/protoc_wrap.sh"`.
