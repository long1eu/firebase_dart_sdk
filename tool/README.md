# tool/

- `test_all.sh [package ...]`: pub get, analyze and test the two published packages, firebase_app_dart and cloud_firestore_dart (unit tests only for cloud_firestore_dart). `TEST_LOG_DIR` keeps the outputs.
- `print_test_failures.sh <log>`: the failed tests of a `dart test --reporter expanded` log with the first lines of each error; the test scripts call it on failure. The scripts name the expanded reporter because `dart test` switches to its `github` reporter under GitHub Actions.
- `start_emulator.sh`, `stop_emulator.sh`: run the Firestore emulator on 127.0.0.1:8080 (project `demo-test`).
  The Firebase CLI is installed locally in `.emulator/` (git-ignored): `mkdir -p .emulator && cd .emulator && npm init -y && npm install firebase-tools`.
  Override the location with `EMULATOR_DIR`. Java is required; the emulator JAR downloads on first start.
- `test_integration.sh [standard|enterprise|both] [dart test arguments...]`: run the cloud_firestore_dart integration tests against emulators that are already running (it never starts or stops one).
  - `standard` (default): `test/integration` against the Standard edition emulator (`FIRESTORE_EMULATOR_HOST`, default 127.0.0.1:8080).
  - `enterprise`: `test/integration` against the Enterprise edition emulator (`FIRESTORE_ENTERPRISE_EMULATOR_HOST`, default 127.0.0.1:8181), then `test/integration_enterprise`.
  - `both`: one after the other. Extra arguments replace the default paths, e.g. `tool/test_integration.sh enterprise test/integration/firebase/firestore/query_test.dart`.
  - `--transport=webchannel` (after the edition): run the same tests over the web transport (REST and WebChannel through `dart:io` HTTP) instead of gRPC, still on the VM. The standard suite passes over it against emulator v1.22.0, with the same counts as over gRPC. `--transport=webchannel-longpolling` does the same with the streams in long polling mode. In these runs the Firestore Lite tests (`test/integration/firebase/firestore/lite_test.dart`) use the transport the lite library has on the web (REST only, `rest_transport.dart`); `FIRESTORE_TEST_TRANSPORT=rest` selects it for that file alone.
  - The full output of each run goes to `TEST_LOG_DIR` (default: a new temp dir); the script prints the failed tests and a summary and exits non-zero on failure.
- By hand, from `cloud_firestore/cloud_firestore_dart`: `FIRESTORE_EMULATOR_HOST=127.0.0.1:8080 dart test test/integration`.
- `start_enterprise_emulator.sh`, `stop_enterprise_emulator.sh`: run a second Firestore emulator in **Enterprise edition** on 127.0.0.1:8181 (project `demo-test`), next to the standard one.
  - It runs the emulator JAR directly (`java -jar ... --database-edition enterprise`), without the Firebase CLI. The JAR is the newest `cloud-firestore-emulator-v*.jar` in `~/.cache/firebase/emulators` (the CLI downloads it on the first start of the standard emulator, or with `firebase setup:emulators:firestore`); set `FIRESTORE_EMULATOR_JAR` to use another one.
  - `ENTERPRISE_EMULATOR_PORT` changes the port, `EMULATOR_DIR` the directory of `enterprise_emulator.pid` and `enterprise_emulator.log` (default `.emulator/`).
  - The pid file holds the pid of that java process. The stop script signals only that pid, and only after checking that it still is a Firestore emulator started with `--database-edition enterprise`; it never touches the standard emulator. The start script refuses to start when the port is already taken by something else.
- Enterprise tests: `FIRESTORE_ENTERPRISE_EMULATOR_HOST=127.0.0.1:8181 dart test test/integration_enterprise` from `cloud_firestore/cloud_firestore_dart`. Without the variable they are skipped (with a reason). Tests that compare the two editions also need `FIRESTORE_EMULATOR_HOST`.
- Environment variables read by the tests (`cloud_firestore/cloud_firestore_dart/test/util/test_backend.dart`):

  | Variable | Meaning |
  | --- | --- |
  | `FIRESTORE_EMULATOR_HOST` | `host:port` of the standard emulator. When set it always wins over a real project. |
  | `FIRESTORE_ENTERPRISE_EMULATOR_HOST` | `host:port` of the Enterprise edition emulator, for `test/integration_enterprise`. |
  | `FIRESTORE_EMULATOR_EDITION` | `standard` or `enterprise`: the edition of the emulator behind `FIRESTORE_EMULATOR_HOST`. `test_integration.sh` sets it; with `enterprise` the tests of the standard suite whose expectations only hold for the Standard edition are skipped. Unset, the edition is Enterprise exactly when both host variables name the same emulator. |
  | `FIRESTORE_TEST_PROJECT_ID` | Opt-in: run the integration suite against this real Firebase project (only while `FIRESTORE_EMULATOR_HOST` is unset). |
  | `FIRESTORE_TEST_DATABASE_ID` | Optional database id in that project (default `(default)`). |
  | `GOOGLE_APPLICATION_CREDENTIALS` | Standard Application Default Credentials variable: path of a service-account key file used for the real project. Without it the gcloud application-default credentials are used. |

  The real-project mode is described in the Testing section of `cloud_firestore/cloud_firestore_dart/README.md`. It is never used unless you set `FIRESTORE_TEST_PROJECT_ID`.
- The standard suite on the Enterprise edition emulator (v1.22.0): everything passes except eleven tests, which `tool/test_integration.sh enterprise` skips with a reason. Nine are behaviour differences of the edition and two are an emulator bug:

  | Difference on Enterprise | Tests skipped |
  | --- | --- |
  | Equality filters (`in`, `array-contains`, `array-contains-any`) match `null` and `NaN`; on Standard they never do. | `query_test`: `testQueriesCanUseInFilters`, `testQueriesCanUseArrayContainsFilters`, `testQueriesCanUseArrayContainsAnyFilters` |
  | `sum` over no documents is `null`, not `0`. | `aggregation_test`: `testPerformsSumAndAverageOverZeroDocuments`; `composite_index_query_test`: `testPerformsAggregationWhenUsingArrayContainsAnyOperator` |
  | An aggregation covers every document of the query; Standard only aggregates over the documents that have all the aggregated fields. | `lite_test`: `performs aggregations on documents with all aggregated fields using getAggregationFromServer` |
  | No limit of 5 aggregations per query. | `aggregation_test`: `testCannotPerformMoreThanMaxAggregations` |
  | An integer `sum` that overflows 64 bits (also only while accumulating) fails with `INVALID_ARGUMENT: Long overflow`; Standard returns a double. | `aggregation_test`: `testPerformsSumThatOverflowsMaxLong`, `testPerformsSumThatIsNegative` |
  | Emulator bug: a Listen with `!=` or `not-in` on the document id fails with `__key__ filter value must be a Key`, although the client sends a reference value and the identical query succeeds with RunQuery on the same emulator (and with Listen on the Standard one). | `query_test`: `testQueriesCanUseNotEqualFiltersWithDocIds`, `testQueriesCanUseNotInFiltersWithDocIds` |

  The first four rows are pinned by `test/integration_enterprise/edition_differences_test.dart`. All of this was observed with the emulator only, not with a production Enterprise database. The JS SDK skips its counterparts of rows 1 to 3 on Enterprise (`it.skipEnterprise`); it has no counterpart of row 4 with real 64-bit integers.
- **Web transport and the emulator.** Browser tests and `--transport=webchannel*` runs go to a private emulator, never to the shared one on 8080:
  - `start_private_emulator.sh [port]` / `stop_private_emulator.sh [port]` (default 8090) run the emulator JAR in Standard edition with their own pid file and log. `test_integration.sh --transport=webchannel*` defaults to 127.0.0.1:8090, and the browser tests are compiled for that port.
  - `build_web_test_assets.sh` fetches or builds the files the browser tests load at run time and that are not in the repository: `test/browser/sqlite3.wasm` (downloaded, accepted only with the sha256 pinned in the script) and `test/browser/crash/crash_worker.js` (compiled with `dart compile js -O1`, rebuilt when its sources changed). `test_browser.sh` and `test_unit_browser.sh` call it; new assets go there as one more section.
  - `test_unit_browser.sh` runs the unit tests of the SQLite layer (`test/unit/firebase/firestore/local/sqlite_*_test.dart`) in Chrome with dart2js, on the WebAssembly build of SQLite; no emulator. Four files are left out, with the reason in the script: two import `dart:io`, and `sqlite_field_index_manager_test.dart` and `sqlite_lru_garbage_collector_test.dart` each have one test that fails with dart2js.
  - `test_browser.sh [dart2wasm|dart2js|both]` runs `test/browser` in Chrome with `-j 1` and starts (and stops) the private emulator if needed. It passes the test files in name order (`web_persistence_reload_2_read_test.dart` must load after `..._1_write_test.dart`) and downloads `test/browser/sqlite3.wasm` for the persistence tests: the asset of the `sqlite3-<version>` release of `simolus3/sqlite3.dart` for the version in `pubspec.lock`, accepted only with the sha256 pinned in the script (update `SQLITE3_WASM_VERSION` and `SQLITE3_WASM_SHA256` together when the dependency moves; `SQLITE3_WASM=<file>` uses a local file instead). The persistence tests (`web_persistence*_test.dart`) need `test/browser/sqlite3.wasm`, the WebAssembly build of the resolved `sqlite3` version from the releases of that package (not in the repository); without it they skip themselves with a reason. `web_persistence_reload_2_read_test.dart` has to be loaded after `web_persistence_reload_1_write_test.dart` in the same run: pass the files in that order (the runner keeps the order of its arguments, not of a directory), otherwise the second one skips itself with a reason. `web_persistence_crash_test.dart` (300 kills of a worker in the middle of its writes, about 45 s) also needs `test/browser/crash/crash_worker.js`, compiled by `tool/build_web_test_assets.sh` (which `test_browser.sh` runs; the file is git-ignored and includes the example opener, so it is rebuilt every time), and only runs with `-c dart2js`: under dart2wasm it skips itself with a reason. The SQLite-backed unit tests (`test/unit/firebase/firestore/local/sqlite_*_test.dart` and the other tests on `DatabaseMock`) run in Chrome too, `dart test -p chrome -c dart2js <files>`, through `test/util/sqlite3_database_web.dart` (the WebAssembly SQLite on an in-memory file system); they need the same `sqlite3.wasm`.
  - Why private: the emulator (v1.22.0) keeps the socket of an aborted WebChannel back-channel request when the session was not terminated. Measured on a fresh emulator with 20 sessions each: handshake only, handshake + terminate, a long poll that completes, an aborted back channel followed by terminate, and terminate while the back channel is open leave nothing behind; an aborted back channel without terminate leaves one file descriptor per session, later listed by `lsof` as a `CLOSED` TCP socket, until a garbage collection of the emulator (20 went down to 2 in about four minutes; 38 others stayed for more than five).
  - The client caused them: when a client was terminated its HTTP layer was closed right after the terminate requests were issued, which cut them off. One run of `firestore_test.dart` (66 tests) over the web transport left 105 file descriptors (81 `CLOSED` sockets 45 s later) on a fresh emulator; with the fix (sessions are always terminated, also when closed during their handshake, and the HTTP layer waits for that) the same run leaves 4 and no `CLOSED` socket. A browser tab that is closed still cannot terminate its sessions.
  - Restart the private emulator after a few web runs. The emulator starts one thread per WebChannel session (`com.google.net.webchannel.server.common.ChannelProcessor.run`, seen with `jstack`) and never ends it, also when the session was terminated properly: 20 sessions of any kind add 20 threads, which were still there minutes later. One run of the standard suite over the web transport opens about 1100 sessions. On macOS a process may have 8192 threads (`kern.num_taskthreads`): the emulator then logs `pthread_create failed (EAGAIN)`, stops answering (requests time out, or REST answers 500 "Panic! This is a bug!") and finally exits. A private emulator died that way after about six suite runs plus the chaos tests; this is also what broke the shared emulator. The client cannot avoid it. `test_browser.sh` uses a fresh emulator when it starts one itself, and CI restarts it between the two web suite runs.
  - A listen that returns more than about 10,000 documents fails over WebChannel on the emulator (v1.22.0), streaming or long polling: the emulator queues at most 10,000 messages for the back channel, logs `Failed to send a new message due to too many pending messagings in the back channel (10001)` and drops the session, which the client sees as HTTP 404 and `unavailable`. Measured on the VM with a collection of 12,000 documents: limits of 9,000 and 9,990 work, 10,500 and 12,000 fail; over gRPC all four work. The client cannot avoid it (the messages pile up on the server); read large collections in pages against the emulator. Not checked: the JS SDK against the emulator, and the production backend.
  - Why `-j 1` for the browser tests: Chrome allows six connections per host over HTTP/1.1, which is what the emulator speaks, and they are shared by all tabs. A client holds up to two long-lived requests (listen and write) plus its unary calls; a single test page was measured at up to 6 requests in flight and the three test files side by side at 5 + 6 + 6. Requests then wait in the browser: first tests failed with "Request time out" after the 15 s unary timeout, with `unavailable` on a server read, or with a listener that never synced, in about one parallel run out of six. Five serial runs in a row passed in 7 to 8 s each. The production backend speaks HTTP/2, where the limit does not apply (not verified).
- `check_size.sh` compiles the two programs of `tool/size` (the same small application with Firestore Lite, `lite_app.dart`, and with the main library and a memory cache, `full_app.dart`) with `dart compile js -O2` and prints the size of the JavaScript, raw and gzipped, and how much of it is code of `cloud_firestore_dart`. It fails when the compiler's `--dump-info` output lists code of the local store, the sync engine, the views, the remote store, bundles or the WebChannel transport in the lite program, or when the lite program is over the budget in `tool/size/check_size.dart` (450,000 characters, 140,000 bytes gzipped; measured 415,850 and 128,303 with Dart 3.12.2). The numbers move with the Dart SDK, so compare runs of the same SDK. `SIZE_OUT_DIR` keeps the compiled programs and the dumps.
- CI (`.github/workflows/ci.yml`) has eight jobs: unit tests (`test_all.sh`) on the lowest supported Dart (3.8.0, with the formatting check of `lib` and `example`) and again on stable, the standard suite on the Standard emulator plus `test/production` (`test_integration.sh standard`), the same suite over the web transport and again with long polling (`test_integration.sh standard --transport=webchannel`, `--transport=webchannel-longpolling`, against a private emulator), the browser tests in headless Chrome (`test_browser.sh both`) followed by the SQLite unit tests in Chrome (`test_unit_browser.sh`), the Enterprise tests (`test/integration_enterprise` with both emulators), and the standard suite on the Enterprise emulator (`test_integration.sh enterprise test/integration`). The standard jobs also install `interop/` so that the JS interop tests run. The eighth is the Firestore Lite size check (`check_size.sh`, on Dart 3.12.2). The unit tests, the standard suite (over gRPC and over the web transport) and the Enterprise tests are required; the browser tests, the Auth emulator tests, the standard suite on the Enterprise emulator and the size check are allowed to fail. The unit job on stable also runs the connectivity test that adds a network interface, as root (allowed to fail until it has passed on a runner). All jobs run on `ubuntu-26.04`, named explicitly: it is the image `ubuntu-latest` resolved to in every run so far, and the jobs use its Chrome, libsqlite3 and openssl.
- Chaos tests: `test/integration/firebase/firestore/chaos/` in `cloud_firestore/cloud_firestore_dart` puts a test-only TCP proxy (`test/util/chaos_proxy.dart`) between a client and the emulator and cuts, stalls or delays the connection. They run with the integration suite (emulator only). The randomized soak test is short by default: `CHAOS_SOAK_SECONDS` (default 4), `CHAOS_SOAK_CLIENTS` (default 3) and `CHAOS_SOAK_SEED` make it longer or repeat a run; on failure it prints the seed and the log of the operations. They also run over the web transport (`--transport=webchannel` and `webchannel-longpolling`, the proxy is at TCP level): every scenario passes there except one that is skipped with a reason (it needs two increments in flight at once, and the web transport never sends an increment before the answers to the earlier writes arrived).
- `start_auth_emulators.sh`, `stop_auth_emulators.sh` `[auth port] [firestore port]` (defaults 9197 and 8197): the Firebase Auth emulator (needs the firebase CLI, see above) and a private Firestore emulator whose rules require a signed-in user (`auth_emulators/firestore.rules`), for `firebase_auth/firebase_auth_providers_dart/test/auth_emulator_test.dart` and `cloud_firestore/cloud_firestore_dart/test/integration_auth`. The start script prints the two variables to export (`FIREBASE_AUTH_EMULATOR_HOST`, `FIRESTORE_AUTH_RULES_EMULATOR_HOST`); the tests are skipped without them. Each emulator is stopped by its own pid; the shared emulators and their rules are not touched.
- `linux/run_in_container.sh [unit|integration|all] [linux/arm64|linux/amd64]`: the unit tests (`test_all.sh`) and the standard integration suite (`test_integration.sh standard`) in a Linux container (Docker; image from `linux/Dockerfile`: `dart:stable` on Debian, Java 21, only the runtime package of SQLite). The emulator runs inside the container from the JAR in `~/.cache/firebase/emulators` (copied in, never modified), so no emulator of the host is used. The container gets `CAP_NET_ADMIN` and `FIRESTORE_TEST_NET_ADMIN=1` for the connectivity test that adds a network interface (`connectivity_interface_change_test.dart`). It is named `fsdart-linux-test-<arch>-<pid>` and removed on exit; logs go to `TEST_LOG_DIR`. The platform that is not the one of the Docker server runs emulated. On an Apple silicon Mac (Rosetta), x64 fails three unit tests every time, all sensitive to how fast code first runs: `exponential_backoff_test` (first attempt under 50 ms), `task_scheduler_test` `canScheduleTasksInTheFuture` (timers 4 ms apart) and `cancelled_call_close_test` (times out); they pass natively on arm64, and the unit job of CI runs them on x64.
- `interop/`: Node harness for the interop tests with the JS SDK and firebase-admin (`npm install` there; see its README).
- `bench/`: micro-benchmarks for hot paths.
- Regenerating the Firestore protos: `cloud_firestore/cloud_firestore_dart/tool/gen_protos.sh` (needs `protoc_plugin` 25.1.0, matching protobuf 6.x; set `PROTOC_GEN_DART` to use a `protoc-gen-dart` that is not on `PATH`). The well-known types (`google/protobuf/*.proto`) are not generated: they come from `package:protobuf/well_known_types`. If `protoc` is unusable, set up `tool/protoc_wrap.sh` (see its header) and pass `PROTOC="$PWD/tool/protoc_wrap.sh"`.
